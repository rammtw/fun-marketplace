# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Фронтенд площадки игровых товаров и услуг: витрина игр, каталог лотов по игре,
карточка лота с покупкой, заказы, кошелёк, рабочий стол продавца со своими лотами,
регистрация и вход. Бэкенд лежит рядом — `../fun-marketplace-backend` (JSON API + JWT,
без своего фронта); его `CLAUDE.md`, `AGENTS.md` и `docs/architecture.md` описывают
домен и решения, перед доменной работой читать их, а не догадываться по именам полей.

## Команды

```bash
npm start                    # dev-сервер на :3000
npm run build
npm test                     # watch-режим CRA
npm run typecheck            # tsc --noEmit
CI=true npx react-scripts test src/app/App.test.tsx -t "гостю показываются вход и регистрация"
```

Отдельной команды линта нет: конфиг `react-app` зашит в `package.json` и работает
только внутри `react-scripts` — ошибки видно в консоли dev-сервера и в `build`.
`CI=true npm run build` считает предупреждения ошибками, этим и проверяется линт.

## Типы API генерируются, а не пишутся

```bash
npm run api:sync             # = api:schema + api:types
```

`api:schema` копирует `docs/openapi.json` бэкенда в `src/shared/api/openapi.json`.
Путь к бэкенду задаёт переменная `BACKEND_DIR` (по умолчанию `../fun-marketplace-backend`).
Постоянно — строкой `BACKEND_DIR=/path/to/backend` в `.env.local`: файл в `.gitignore`,
скрипт читает его через `node --env-file-if-exists` (нужен Node ≥ 22.9), а CRA переменные
без префикса `REACT_APP_` в бандл не пускает. Разово — `BACKEND_DIR=... npm run api:sync`,
окружение важнее файла.
`api:types` прогоняет спеку через `openapi-typescript` в `src/shared/api/schema.d.ts`.
`schema.d.ts` — артефакт, руками не править; удобные имена для типов из него живут
в `src/shared/api/contract.ts`. Контракт поменялся —
сначала в бэкенде `make openapi`, потом здесь `npm run api:sync`. Сама спека лежит
в репозитории, так что читать контракт можно и без поднятого бэкенда.

## Бэкенд под рукой

В `../fun-marketplace-backend`: `make up` поднимает стек, `make fixtures` заливает игры,
лоты и аккаунты. API — `http://localhost:8080`, Swagger UI — `/api/doc`, письма —
Mailpit на `http://localhost:8025`.

Запросы уходят относительными путями (`/api/...`): в разработке их проксирует
dev-сервер CRA (`"proxy"` в `package.json`), поэтому CORS на бэкенде не нужен —
бандла nelmio/cors там и нет. Для сборки на другой хост адрес задаётся
`REACT_APP_API_URL` (CRA пробрасывает в бандл только переменные с этим префиксом),
читается он в `src/shared/config/api.ts`. Побочный эффект прокси: запрос без
`Accept: text/html` уходит на бэкенд, так что `curl http://localhost:3000/games/x`
вернёт 404 от Symfony, а браузер получит index.html.

## Что важно в контракте

- **Аутентификация.** `POST /api/auth/login` → `{ token }`, дальше заголовок
  `Authorization: Bearer`. Почта подтверждается по ссылке из письма; до подтверждения
  login отвечает 401 с готовым для показа `message`, повторное письмо —
  `/api/auth/resend-confirmation`. Ссылка из письма ведёт прямо в API
  (`GET /api/auth/confirm`), страница `/confirm` на фронте — для случая, когда
  токен открывают через него.
- **Регистрация идёт под редакцию политики.** Форма сначала берёт действующую
  редакцию (`GET /api/privacy/policy`, открыта всем) и показывает её номер ссылкой
  на страницу `/privacy`, где лежит текст целиком (в новой вкладке — заполненная
  форма не должна теряться), а в `POST /api/auth/register` возвращает
  `policyVersion` вместе с согласиями: обязательно и по умолчанию снято только
  `personalDataConsent` (на бэкенде `Assert\IsTrue`), `marketingConsent` — по желанию.
  Возраст площадка больше не собирает, `publicProfileConsent` форма не шлёт:
  показ профиля в открытой части — отдельное согласие на распространение, даётся
  потом через `POST /api/privacy/consents` с целью `distribution`.
  `publicProfileConsent` форма не шлёт вовсе: показ профиля в открытой части —
  отдельное согласие на распространение, в регистрации его не спрашиваем, и без
  поля бэкенд считает его неданным. Дать его потом — `POST /api/privacy/consents`
  с целью `distribution`. Без политики регистрировать некого, поэтому при неудачной загрузке
  форма отключается. 409 на регистрации значит и «почта занята», и «политику
  переиздали», а тела у ответа нет: `pages/register` различает их, перечитав
  политику и сравнив редакцию с отправленной.
- **Текст ошибки** лежит в разных полях: lexik отдаёт `message`, обработчик Symfony —
  problem+json с `detail` и `violations`. Разбирает это `shared/api/client.ts`,
  наружу отдавая `ApiError` со статусом и разобранными нарушениями полей.
- **Деньги** всегда `{ amount, currency }`, где `amount` — целое в минорных единицах
  (копейках). Форматирование только на фронте (`shared/lib/money.ts`), никакой
  арифметики во float.
- **Витрина не фильтрует по остатку.** `GET /api/games/{slug}/offers` отдаёт все активные
  лоты, свежие сверху, в том числе распроданные: `stock: 0` — товар кончился
  (`isPurchasable` у него false), `stock: null` — услуга, остатка у неё нет вовсе. Каталог
  на фронте гасит распроданные и опускает их в конец списка (`pages/game/lib/stock.ts`).
- **В витринном лоте нет продавца.** `OfferSummary` его не несёт (в отличие от
  `OfferDetails.seller`), поэтому каталог узнаёт свои лоты, сверяя их со своим списком
  (`GET /api/offers/mine?status=active`) и разводя по группам «Ваши» и «Остальные».
  Запрос вспомогательный: он идёт только у вошедшего и при отказе молча даёт пустой
  список — каталог из-за него ломаться не должен.
- **Публичное против приватного.** Витрина (`/api/games`, `/api/games/{slug}/offers`,
  `/api/offers/{id}`, `/api/users`) открыта; кошелёк и заказы требуют токен.
- **Покупка** `POST /api/orders` различает исходы кодами: 402 — не хватает денег на
  кошельке, 403 — свой же лот, 404 — лота нет, 409 — лот снят или единиц меньше
  запрошенного, 422 — валидация. Эти случаи в UI разные, общей «ошибки» мало, разбирает
  их `pages/offer/ui/PurchasePanel.tsx`. Текст 402 с бэкенда показывать нельзя — там
  суммы в копейках («На счету 12300, требуется 45600»), нехватку считаем сами по балансу
  и ведём на `/wallet?need=<копейки>`.
- **Пополнение и вывод идут через ЮKassa.** `POST /api/wallet/deposits` заводит платёж
  и отдаёт `confirmationUrl` — адрес, куда человека уводят платить; деньги на балансе
  появляются не здесь. `returnUrl` обязан вести на домен площадки (иначе 422), а
  зачисляет деньги `GET /api/wallet/deposits/{id}`: она сама спрашивает провайдера,
  поэтому кошелёк при загрузке опрашивает свои незавершённые операции, а не ждёт
  вебхука. `POST /api/wallet/payouts` — вывод по `payoutToken` (синоним карты из
  виджета ЮKassa; номер карты площадка не принимает и не хранит), сумма сразу уходит
  в удержание: 409 — не хватило свободных денег, 422 — меньше 100 ₽ или нет синонима,
  502 — провайдер не ответил и операция не заведена. Статусы у обеих операций одни:
  `pending → succeeded | canceled`. Суммы в копейках, рубли из формы переводит
  `parseAmountToMinor`; текст 409 показывать нельзя — там копейки, нехватку считаем
  сами по балансу.
- **Список заказов** `GET /api/orders` отдаёт страницу `{ items, page, perPage, total }`
  с `OrderSummary` (не `OrderView`): `role=buyer|seller` переключает покупки и продажи,
  `status` фильтрует, чужие заказы не попадают туда ни при каких параметрах. Неизвестный
  статус или роль — 422, поэтому значения из query-параметров сверяются со словарём
  `entities/order` перед отправкой.
- **Заказ** идёт по статусам `placed → paid → delivered → completed` (плюс `cancelled`,
  `disputed`, `refunded`). Товар (`kind: goods`) выдаётся сразу, услуга (`service`)
  ждёт продавца; `deliveryType` — `auto`/`manual`.
- **Ручная выдача.** `POST /api/orders/{id}/deliver` с `{ note }` закрывает выдачу за
  продавцом: 403 — по заказу вы покупатель, 409 — заказ не в `paid` (уже выдан или
  автовыдача закрыла его при покупке), 422 — пустой `note`. Ответ — весь `OrderView`,
  второй запрос не нужен; `note` приезжает обеим сторонам как `deliveryNote` и до
  появления чата это единственный канал от продавца к покупателю. Ждущий выдачи заказ
  в UI опознаётся по `status: paid` (снимка `deliveryType` в заказе нет). Очередь
  выдачи одного лота — `GET /api/orders?role=seller&status=paid&offerId=<id>`; на
  кривой uuid ручка отвечает 422, поэтому значение сверяется с формой uuid перед отправкой.
- **Раздел игры** несёт `attributeSchema` — схему атрибутов лота: поле => `{ type: int |
  string | bool | enum, values, required }`. Формы лота строятся по ней, а не хардкодом под
  конкретную игру, и типы обязаны совпасть: `int` — число, `bool` — булево, значение `enum` —
  ровно то, что в `values`. Лишнее поле бэкенд тоже не примет (это обычно опечатка в имени).
  Разбор схемы и сборка payload — `pages/offer-editor/lib/attribute-schema.ts`.
- **Лоты продавца.** `POST /api/offers` заводит лот всегда черновиком, `GET /api/offers/mine`
  отдаёт свои лоты во всех статусах, `PATCH /api/offers/{id}` правит переданные поля
  (публикация, снятие и архив — это тоже `status`), `DELETE` — это архив, а не удаление:
  на лот ссылаются заказы. `POST /api/offers/{id}/items` доливает единицы товара с
  автовыдачей; удалить единицу нельзя. Правила, за нарушение которых прилетает 422:
  услуга бывает только с ручной выдачей, автовыдача заводится сразу с единицами, ручная —
  без них, вернуть лот в черновики нельзя, архивный лот не правится (409).
- **Допуск к продаже.** Лот заводит только тот, кто принял правила и сдал по ним тест:
  `GET /api/selling/rules` (открыта всем) отдаёт текст и номер редакции,
  `GET`/`POST /api/selling/admission` — допуск и принятие под этот номер,
  `GET`/`POST /api/selling/exam` — вопросы и ответы. Верных вариантов в вопросах нет
  и не будет; несданный тест отвечает не разбором, а пунктами правил на перечитать,
  после неудачной попытки держится минутная пауза (429). Допуск привязан к редакции,
  а не к аккаунту: новая гасит его всем, поэтому спрашивается он перед каждым
  открытием формы лота (`app/ui/RequireSellingAdmission`), а не однажды при первом.
  403 на `POST /api/offers` и на публикации через `PATCH` — это он; снять лот
  с витрины и убрать в архив можно и без допуска.
- **Черновик не виден через `GET /api/offers/{id}`** — эта ручка отдаёт только
  опубликованные лоты. Поэтому редактор берёт лот из `GET /api/offers/mine` и ищет по id,
  а схему атрибутов — из карточки игры по `section.gameSlug`.

## Раскладка кода: FSD

Установлены две skill'ы (`.claude/skills`, `.agents/skills`, версии в
`skills-lock.json`): `feature-sliced-design` (v2.1) и `vercel-react-best-practices`.
Перед тем как заводить каталоги, читать skill FSD.

```text
src/
  app/        провайдеры, роутер, макет страницы, глобальные стили, RequireAuth/GuestOnly
  pages/      games, game, offer, order, orders, my-offers, offer-editor, selling,
              wallet, login, register, confirm-email, privacy-policy, not-found
  entities/   wallet (баланс), order и offer (словари статусов)
  shared/     api (клиент + сгенерированные типы), auth (токен и сессия), lib, ui, config
```

`features/` нет, `widgets/` не заводить. В `entities/` попало ровно то, что переросло
страницу:

- `wallet` — баланс нужен шапке, панели покупки и кошельку, и после каждой покупки
  и пополнения он меняется. Пока каждый экран грузил его сам, в шапке оставались старые
  деньги; теперь один `WalletProvider` с единственным `refresh()` — ни покупка, ни
  пополнение, ни выплата баланс в ответе не возвращают. Транспорт при этом остался
  в `shared/api`.
- `order` и `offer` — словари статусов заказа и лота: их читают и списки, и карточки,
  а меняются они вместе с доменом, а не с экраном.

Закрытые токеном маршруты (`/wallet`, `/orders`, `/orders/:id`) обёрнуты в `RequireAuth`:
он запоминает путь в `location.state.from`, и страница входа возвращает туда после входа.
Тем же приёмом работает `RequireSellingAdmission` поверх `/my/offers/new`: без допуска
уводит на `/selling`, а страница правил после сданного теста возвращает в форму.

Запросы страницы лежат в её же `api/`, в `shared/api` остаётся транспорт и то, что
зовут несколько слайсов: каталог (`catalog.ts` — витрина и редактор лота), кошелёк,
рабочий стол продавца (`seller-offers.ts`), допуск к продаже (`selling.ts` — страница
правил и `RequireSellingAdmission` в `app/`) и политика (`privacy.ts` — регистрация
и страница `/privacy`). Импорты абсолютные от `src` (`baseUrl` в `tsconfig.json`),
слайс подключается через свой `index.ts`.

Сессия — `shared/auth`: токен в `localStorage`, `SessionProvider` при старте
дёргает `/api/auth/me` и гасит токен, только если его отверг сервер (401), а не при
сетевой ошибке. `shared/api/client.ts` берёт токен напрямую из `shared/auth/token.ts`,
в обход `index.ts` слайса — иначе получается цикл импортов.

## Ограничения окружения

Сборка — `react-scripts` 5.0.1, из-за него же приколочены TypeScript 4.9 и jest 27
(React при этом 19, react-router 7). Уход на Vite/Next и `eject` — отдельное решение,
не побочный эффект задачи.

Два следствия старого jest, которые ломают тесты, если про них забыть:

- роутер импортируется из `react-router`, а не из `react-router-dom`: jest 27 не умеет
  `exports`-подпути и спотыкается на `react-router/dom`;
- `src/setupTests.ts` доливает `TextEncoder`/`TextDecoder` — в jsdom из jest 27 их нет,
  а react-router читает их при загрузке модуля.

Запросы в тестах глушатся через `shared/api/test-fetch.ts`: клиенту хватает `ok`,
`status` и `text()`. `mockFetchOnce` отвечает на следующий запрос по порядку,
`mockApi` — по ключу «METHOD /path»; когда на странице несколько запросов
(лот + кошелёк + сессия), брать `mockApi`: порядок эффектов — не контракт.
`requestBody('POST', '/api/orders')` достаёт отправленное тело, `requestUrl` — последний
URL с query-параметрами.
